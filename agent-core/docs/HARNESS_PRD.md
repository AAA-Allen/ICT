# Agent Harness 层产品需求文档

状态：草案，供开发排期与验收使用  
基线：`4f52a06`（基础运行层收口）  
适用项目：`agent-core` 0.4.x 之后的增量开发

## 1. 背景与定义

**产品定位：** `agent-core` 是可适配不同领域的 Agent 框架。框架提供通用运行、装配和执行控制能力；领域提示词、工具实现、数据源及业务规则由接入方提供。换领域时应主要替换这些接入内容，而不是改写框架内核。

项目已有 Graph Runtime、Agent 外壳、模型适配器、工具注册表、`agent_loop`、运行持久化、checkpoint 和 HTTP 工作台。它能执行一次模型驱动的工具循环，但执行约束散落在节点配置和运行时中：模型和工具预算不完整，失败时的中间调用事实无法完整查询，人工批准、上下文长度管理、重试与幂等没有统一契约。

本 PRD 中的 **Harness** 是把模型、工具、会话、上下文和执行策略组合成 Agent 的通用装配与执行层。它决定一次 Agent 执行可以看到什么、可以调用什么、何时停止，以及如何留下可追溯的证据。Graph Runtime 继续负责节点调度、状态提交、生命周期和 checkpoint；业务工具及业务规则仍由应用提供。本阶段不建设模型评测平台，评测只作为后续验证 Harness 行为的手段。

## 2. 目标与成功标准

### 目标

1. 让不同领域通过替换模型、工具、会话存储和策略配置组装 Agent，不修改 Graph Runtime。
2. 让模型驱动的执行有明确、可配置、可解释的边界。
3. 让每次模型决策和工具调用在成功、失败、阻断与恢复后都能追溯。
4. 对有副作用的工具提供人工批准和安全的恢复入口。
5. 保持现有 Python API、声明式 Agent 和 HTTP 工作台的主要使用方式；需要破坏性变更时按 0.x 政策记录迁移方式。
6. 所有 Harness 策略都通过通用配置、协议或工具元数据表达，不在框架内写入某个领域的流程或判断规则。

### 发布验收

- 超预算、越权、拒绝批准和模型/工具错误均返回稳定 `reason_code`，不被包装成成功结果。
- 同一 `run_id` 的审计记录能重建模型调用、工具调用、批准决定及最终状态；失败前已发生的调用仍可见。
- 在 checkpoint 恢复后，已消耗的预算和已确认的工具副作用不会被当作全新执行而重复计算或静默重放。
- 默认本地单实例场景可用；重启后运行和会话数据可读取。对跨进程或分布式能力不作承诺。
- 文档示例与实际 API 保持一致，包含正常、超限、失败、批准和恢复路径。
- 同一 Harness 接口可接入至少两个不同领域的示例工具集，无需修改 `agent_core` 源码。
- 模型、工具、会话与循环各有明确的替换边界；替换其中一个实现不要求复制或修改其他组件。

## 3. 用户与使用场景

| 用户 | 主要需求 |
| --- | --- |
| Agent 开发者 | 配置工具、预算、上下文和批准规则，理解一次执行为什么停止。 |
| 业务应用开发者 | 接入自己的模型与工具，不让框架替业务判断外部副作用是否成功。 |
| 运维或审核人员 | 查询调用时间线、参数摘要、结果、原因码和批准记录，定位失败或误操作。 |

核心场景：一个 Agent 接到任务后调用模型，模型可能请求多个工具。Harness 在每次外部调用前执行预算和策略检查，记录尝试与结果；遇到需要批准的工具时暂停并等待明确决定；完成或失败后可按 `run_id` 查询全过程。

## 4. 范围与边界

### 本阶段范围

- 模型适配器、工具注册表、会话存储、Agent loop 和执行策略的装配边界。
- 模型请求与工具执行的有序流水线及其可扩展切入点。
- 单次执行的模型调用次数、工具调用次数和可选时间预算。
- 工具可见性、已声明能力与运行时授权的检查。
- 模型/工具/批准事件的持久化审计；敏感字段按配置脱敏或只保存摘要。
- 会话上下文装配、长度上限和确定性的裁剪规则。
- 有副作用工具的人工批准、拒绝和显式恢复。
- 安全范围内的模型请求重试；工具重试必须有显式幂等契约。

### 暂不纳入

- 分布式队列、多租户权限系统、操作系统级沙箱和跨实例锁。
- 任意 Python 工具的强制中断或 exactly-once 外部副作用保证。
- 内置 RAG、知识库、Planner、模型训练及通用评测平台。
- 由框架自行判断业务工具的外部事实真伪。

能力声明是框架内的调用门禁，不等同于操作系统权限或安全沙箱。服务仍默认仅绑定本机；对外开放前需要独立的认证与隔离设计。

## 5. 功能需求

### H-00 跨领域装配与扩展边界（P0）

- 定义模型适配器、工具提供方、会话存储、Agent loop 和 Harness 策略的最小协议；现有实现作为默认提供方。
- Agent 配置声明所需能力，装配期发现缺失或冲突时明确报错；一个领域 Agent 不依赖另一个领域的工具或数据结构。
- 固定执行切入点与顺序：模型请求前后、工具调用前、工具执行、工具结果处理；策略必须经统一入口执行，节点不能绕过不可跳过的工具门禁。
- 第一阶段以 Python 协议和显式配置为主，不引入热卸载、通用插件市场或复杂 profile 系统。Agent loop 的可替换接口先设计并在后续里程碑落地。

验收：用同一组 Harness 接口装配两个不同领域的 Agent；替换模型适配器或会话存储无需修改 Runtime；工具策略只配置一次便覆盖所有通过 Harness 发起的工具调用。

### H-01 执行预算（P0）

- 配置 `max_model_calls`、`max_tool_calls`，保留现有 `max_rounds` 的兼容入口；参数必须是正整数，装配时拒绝无效配置。
- 在发起模型请求或工具副作用**之前**占用预算。超限时不再发起调用；现有 `max_rounds` 沿用 `MAX_TOOL_ROUNDS`，新增统一模型额度时使用 `MAX_MODEL_CALLS`，工具额度使用 `MAX_TOOL_CALLS`。
- 每次调用记录预算消耗和剩余额度。恢复时从持久化事实重建累计消耗，不重置同一次运行的总预算。
- 第一增量可先实现单次 `agent_loop` 节点范围；扩展到跨节点和恢复范围前，不宣称满足整次运行预算。

验收：给定上限 2 次工具调用，模型请求第 3 次时工具未被执行，运行以 `MAX_TOOL_CALLS` 失败。M1 完成后，查询结果须显示前两次调用及消耗，重启恢复后不能再次获得已用额度。

### H-02 工具暴露与授权（P0）

- 模型只看到当前 Agent 配置允许的工具 schema；工具名重复或 schema 无效在装配时拒绝。
- 模型请求的工具必须存在于当前注册表，并满足已声明能力和运行时策略。未知工具、越权工具沿用稳定阻断原因码。
- 策略返回结构化决定，至少区分允许、阻断和需要批准；调用前授权与调用后结果检查使用不同切入点。
- 可按工具定义 `read_only`、`side_effect`、`requires_approval` 等元数据。未声明副作用属性时采用保守默认值。
- 授权检查在调用前执行；策略变化不能改写已记录的历史事实。

验收：未暴露或未授权的工具请求不会进入工具函数；审计保留请求和阻断原因。

### H-03 执行审计（P0）

- 为模型请求、模型结果、工具请求、工具结果、预算拒绝和批准决定写入有序事件；事件包含 `run_id`、节点/执行 ID、序号、时间、类型、状态及原因码。
- 节点最终失败或阻断时，先前事件仍持久存在。审计写入失败必须显式导致运行失败，不能静默丢失事实。
- 私有会话事实记录保存重建模型所见历史所必需的内容；对外查询默认只返回脱敏摘要。密钥和完整环境变量不得进入两者；提供应用脱敏钩子、存储访问边界及保留策略。
- 每次外部调用生成稳定调用 ID；同一 `run_id` 下的事件顺序与调用 ID 可用于恢复后的预算重建和副作用核对。
- 提供按运行查询的 Python 接口与 HTTP 读取接口；工作台显示同一条时间线。

验收：模型成功请求两个工具，第二个工具失败；查询仍能看到第一次工具成功、第二次工具失败及最终原因码，顺序一致。

### H-04 上下文装配（P1）

- 明确系统指令、会话历史、当前输入和工具结果的拼装顺序，不能让工具结果伪装为系统指令。
- 提供消息数量或字符长度上限；超限时按公开的确定性规则裁剪，保留系统指令和当前用户输入。
- 若适配器提供真实 token usage，记录实际用量；不提供时标记为未知，不估算为真实 token 数。
- 会话写入仅在回复成功且通过格式校验后提交；失败时保留原有会话历史。

验收：同一会话历史在相同配置下生成相同模型消息序列；超限时裁剪结果和原因可查询。

### H-05 人工批准与恢复（P1）

- 对 `requires_approval` 的工具，在调用前进入明确的等待状态，展示工具名、参数摘要、风险提示和请求 ID。
- 只有显式批准才能继续；拒绝产生稳定终态和原因码。重复提交同一决定必须幂等，冲突决定必须拒绝。
- 批准信息与 checkpoint 一起持久化，重启后仍能查询并继续；恢复前再次校验工具及其参数摘要，防止批准错配。
- 待批准请求由服务端保存；客户端只提交批准决定及其 ID，不提交可替换工具参数或运行快照。审批人的身份与授权由宿主应用校验；无此能力时 HTTP 批准入口仅限本机开发使用。
- 这项能力需要为 Runtime 增加最小的等待/恢复契约，不能把“等待”伪装成失败或阻断。

验收：批准前工具执行次数为 0；重启后批准并恢复，工具最多执行一次；拒绝后工具始终不执行。

### H-06 重试与幂等（P2）

- 模型请求仅对明确的瞬态错误允许有限次数重试，记录每次尝试、退避时间和最终结果。
- 工具默认不自动重试。有副作用工具只有在应用提供稳定幂等键及可验证的幂等契约后才能启用重试。
- 取消、预算耗尽、拒绝批准、越权和参数错误不重试。

验收：模型瞬态失败后的重试次数不超过配置；有副作用工具在无幂等声明时只调用一次。

## 6. 接口与数据契约

第一阶段保持 `agent_loop` JSON 配置可用。`max_rounds` 是现有字段；新增 `max_tool_calls`。后续引入统一 `harness` 配置块时，需提供旧字段到新字段的明确映射，并在一个 0.x 次版本内保留兼容读取。

审计事件建议使用追加式结构，最少包含：

```json
{
  "schema_version": 1,
  "run_id": "...",
  "sequence": 1,
  "event_type": "tool.requested",
  "node_id": "...",
  "occurred_at": "...",
  "status": "PENDING",
  "reason_code": null,
  "summary": {}
}
```

这是目标契约草案，字段名称在 H-03 实现时定稿。事件必须有版本、顺序和关联 ID；审计文件损坏或版本不支持时给出明确错误，不把损坏数据当作空历史。

内部的模型可见会话事实与对外审计视图是两个读取面：前者用于恢复和历史投影，后者默认脱敏用于排障。不能用只有摘要的审计视图反推完整模型消息。

## 8. 风险与待定决策

1. **审计与隐私**：完整请求和工具输出可能含敏感数据。M1 先确定默认摘要字段和脱敏钩子，再开放持久化内容。
2. **恢复与副作用**：M4 在副作用工具执行前持久化一次性领取；结果未落盘时返回 `TOOL_OUTCOME_UNKNOWN` 并要求人工核对。M5 的自动重试仍须由应用提供稳定幂等键和可验证的外部契约。
3. **预算作用域**：M6 可选覆盖同一 `run_id` 的 `llm` 与 `agent_loop` 调用，以及同步委派的子 Agent Harness 调用；M7 增加普通 `tool` 节点。应用直接调用模型/注册表、异步和跨进程子 Agent 的累计额度仍需显式接入。
4. **批准入口**：`WAITING_APPROVAL` 和显式恢复已实现；本机 HTTP 审批与核对接口尚无宿主应用身份认证。
5. **默认额度**：M0 暂用 `max_rounds=4`、`max_tool_calls=16`。发布前需依据实际用例确认默认值及其迁移影响。
