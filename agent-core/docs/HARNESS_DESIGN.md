# Harness 层设计说明

状态：设计草案  
基线：`4f52a06`（基础运行底座收口）  
需求、里程碑和验收标准：[Harness PRD](HARNESS_PRD.md)

开源项目对比及设计取舍：[Harness 开源项目调研](HARNESS_OPEN_SOURCE_REVIEW.md)

## 一句话定义

**Harness 是通用 Agent 框架中的装配与执行层。** 它把模型、工具、上下文、会话和执行策略组合为可运行的 Agent，并把模型决策转成受约束、可追溯的行动；不包含特定领域的知识或业务流程。

`agent-core` 的目标始终是适配不同领域。应用可以换模型、提示词、工具、数据源和业务规则，仍复用同一套 Runtime 与 Harness。

## 在框架中的位置

```text
领域应用
  提供提示词、工具实现、数据源、业务规则
       │
       ▼
Agent 装配层
  选择模型、工具、节点和策略配置
       │
       ▼
Harness 层
  组合模型/工具/会话/循环 → 装配上下文 → 暴露可用工具
  → 检查预算/权限/批准 → 调用模型或工具 → 记录事实
  → 决定继续或停止
       │
       ▼
Graph Runtime
  调度节点、提交状态、管理生命周期、Trace 和 checkpoint
```

Harness 在现有实现中通过 Agent 节点接入 Runtime；长期应提供清楚的组件接口，使 Agent loop、上下文装配和工具策略可以替换，而无需修改 Graph Runtime。Runtime 不需要知道“建模”“学习”“测试”等领域词汇；Harness 也不需要知道工具输出在业务上是否正确。

## 设计原则

1. **领域无关。** 策略通过配置、协议和工具元数据表达。框架只识别“调用次数”“是否有副作用”“是否需要批准”等通用属性，不内置领域规则。
2. **能力可组合。** 模型适配器、工具提供方、会话存储、Agent loop 和执行策略各有明确接口；不同领域通过装配这些能力建立 Agent，而不改写框架。
3. **先检查，后行动。** 模型请求工具后，先确认工具可见、参数有效、能力允许、预算充足以及批准状态，然后才调用真实工具。拒绝时不产生工具副作用。
4. **事实独立于最终结果。** 运行失败不能抹去先前已发生的模型和工具调用。审计记录与成功状态更新分开保存。
5. **边界显式。** 无模型、未知工具、越权、超预算、拒绝批准和执行异常分别给出稳定原因码；不把模拟值或异常消息当作成功证据。
6. **恢复以已发生事实为准。** checkpoint 记录位置，调用审计记录尝试与结果。恢复时重新核对预算和外部副作用，不能仅凭 checkpoint 推断工具尚未执行。
7. **默认保守。** 有副作用工具不自动重试；能力声明只是框架门禁，不作为系统级安全隔离。

## 一次执行如何经过 Harness

1. Agent 装配层给 Harness 提供模型适配器、候选工具、会话上下文和策略配置。
2. Harness 根据配置构造模型消息和可见工具 schema，记录模型请求，调用模型。
3. 模型返回文本时，Harness 校验响应并将结果交给节点；Runtime 再决定是否提交状态。
4. 模型返回工具请求时，Harness 校验请求形状和工具名称，然后在调用前依次检查能力、预算与批准要求。
5. 允许调用时，Harness 写入请求事件，调用工具，写入结果事件，再把工具结果作为下一轮模型输入。
6. 任一检查或调用失败时，Harness 产生明确的停止原因；已经写入的调用事实仍可查询。

这一顺序要求“审计写入失败”不能被忽略。未来的审计存储需要定义原子性和故障语义，避免工具已经执行但请求事实没有留下。

## 核心组件与契约

| 组件 | 负责 | 不负责 |
| --- | --- | --- |
| `HarnessLimits` / `HarnessBudget` | 调用前计数和限额判断 | 估算真实 token 或费用 |
| 能力装配（规划中） | 通过小协议选择模型、工具、会话存储、循环和策略实现 | 强制应用使用某个模型或领域工具 |
| 上下文装配器（规划中） | 拼装系统指令、历史、当前输入与工具结果；按确定性规则裁剪 | 生成领域知识 |
| 工具策略（规划中） | 工具可见性、能力、批准和重试许可 | 判断工具业务结果是否可信 |
| 调用审计（规划中） | 记录模型、工具、批准及预算事件，提供查询 | 替代 Runtime 的状态与生命周期记录 |
| 批准协调器（规划中） | 暂停、批准/拒绝和显式恢复 | 自动代替人做批准决定 |

模型适配器维持小协议：接收消息与可见工具定义，返回内容或结构化工具请求；具体模型 SDK、认证和网络连接由适配器处理。工具执行仍经 `ToolRegistry`，沿用现有能力门禁和结构化结果。Harness 不直接调用应用内部函数来绕过注册表。

## 状态与预算作用域

- **节点状态**由 Runtime 管理。只有节点成功时，更新才提交到运行状态；阻断或失败不提交业务状态。
- **调用事实**由 Harness 审计管理。它不随节点失败回滚，因为外部调用可能已经发生。
- **会话事实**应保存重建模型所见历史所必需的内容，历史从事实投影；对外审计视图默认脱敏。现有会话内存直接保存消息，迁移到事件事实模型是 M1 的工作。
- **预算**最终以整次运行累计为目标，恢复后继续消耗既有额度。子 Agent 的额度继承方式在 PRD 的待定决策中明确。

当前工作区已有 `ModelToolLoop` 默认实现、`ModelInvocationPipeline` 和 `ToolInvocationPipeline` 两个调用入口。Python 调用方可向 `agent_loop_node` 注入自定义循环；声明式 JSON 装配仍使用默认循环，尚未提供循环提供方配置。预算只覆盖 `agent_loop` 单次执行：`max_rounds` 默认为 4，`max_tool_calls` 默认为 16；分别以 `MAX_TOOL_ROUNDS`、`MAX_TOOL_CALLS` 停止。它尚未覆盖恢复后的累计预算。M0 组件与完整单元测试已通过，代码待提交。

## 跨领域复用示例

| 领域 | 应用接入的内容 | 复用的 Harness 能力 |
| --- | --- | --- |
| 学习助手 | 检索教材、生成练习、记录进度的工具及提示词 | 工具可见性、调用预算、过程审计、修改进度前批准 |
| 建模助手 | 查询模型、创建元素、修改关系的工具及规则 | 同一套预算与审计、写操作批准、失败停止与恢复 |

这两类 Agent 不应需要修改 `agent_core` 源码。差异属于接入配置和业务工具实现。

## 开发顺序

先定可替换组件的边界，再完成预算与调用审计，随后建立统一工具流水线和上下文管理；人工批准依赖可靠的审计与恢复契约，重试与幂等放在最后。完整需求编号、依赖和验收见 [Harness PRD](HARNESS_PRD.md)。[开源项目调研](HARNESS_OPEN_SOURCE_REVIEW.md)记录了 DeepSeek Harness 等项目的参考机制与取舍。

`agent_lite` 仍是独立的极简入口。Harness 首先服务于 `agent_core` 的完整运行时，不要求轻量包承载持久化、批准或图生命周期能力。
