## 整体判断

项目已经形成可用于受控单机应用的 Agent 执行底座：图编排、受管模型和工具调用、权限与额度、持久审计、审批、checkpoint 和显式恢复都有实现及回归证据。它的主要价值是让调用过程可约束、失败事实可解释、已知副作用可核对。

成熟度目前是“具备工程验证的单机框架，正在准备候选交付”。真实模型任务质量、长期运行资源边界和工作台完整任务闭环仍需补齐。当前证据支持内部试用与 SDK 接入，不足以给出公开候选版本验收通过或多人共享服务就绪的结论。

下一阶段的目标应是让使用者从工作台完成一个受控工具型任务，并在长输出、断线、审批和重启时仍看得清事实。围绕这个目标推进流式可靠性、任务展示和参考应用，可以检验现有内核是否真正方便接入。

## 需要优先解决的具体问题

### 1. 长流输出可能漏读，优先级 P0

`agent_core/streaming.py` 的历史是有界 deque，`history(after=...)` 把 after 当作当前列表下标。`agent_core/http_api.py` 的 SSE 消费者却持续累计 token_index。旧片段被淘汰后，下标与累计进度不再对应。

本轮以 max_history=2 复现：首次读取 a、b 后游标为 2，再发布 c；缓存已变为 b、c，此时 history(after=2) 返回空。默认容量更大，但采用同一分支。该探针复现的是 TokenBus 层缺陷，HTTP 路径已通过源码确认使用同一种下标；本轮未模拟完整 HTTP 长流。

同时，SSE 不发送可用于 token 去重的稳定事件游标，也不读取 Last-Event-ID；前端 EventSource 重连后继续追加文本。重连重复与缺口属于已识别的代码路径风险，需要在 M12 先补端到端回归，再确定协议。

### 2. 流缓存缺少跨运行回收，优先级 P1

TokenBus.close 仅标记关闭，forget 暂无应用调用方；本轮创建并关闭 100 个独立运行后，100 个历史仍可读取。单运行按事件数量限额，并不限制总运行数或单事件字节数。

这证明缓存会保留已关闭运行，尚未测得实际内存耗尽阈值。下一步应定义运行结束后的保留期、全局容量与字节上限，并保护活动运行、同一运行后续模型节点和晚订阅者。

### 3. 适配器的响应上限不一致，优先级 P1

普通 complete 有响应字节上限；complete_with_tools 使用无长度参数的 response.read，流式路径也需统一核对帧、累计输出和工具参数大小。该差异已从源码确认，恶意或异常大响应的端到端影响尚未注入验证，应作为 M12 的定向边界测试。

### 4. 内核执行事实尚未完整传递到使用界面，优先级 P1

后端可查 harness-events，但工作台目前没有调用该接口。用户能看到节点与最终原因码，却不能直接核对模型/工具尝试、重试、预算占用、usage 覆盖率及恢复阻断依据。

审批界面也主要显示工具、请求 ID 和参数摘要。受控写入应有工具声明的、允许展示的动作说明；不能把私有参数全文直接暴露来解决可理解性。审批 token 的浏览器使用缺口已在文档声明，需要在本机应用闭环中处理。

### 5. 真实任务与交付证据仍有缺口，优先级 P1，并行推进

M10 外部模型报告、摘要人工复查、远端 CI、许可证及版本决策仍未完成。缺少配置是外部条件，不是增加内核功能可以替代的验收。

现有两个场景适合检查固定任务和执行规则，但不能替代一个实际由模型选择只读工具、形成产物、经批准写入的应用闭环。新的参考应用应放在 examples，保持领域规则和路径约束在应用/工具层。

## 架构与产品方向

继续以 agent_core 为主要运行底座，面向本机工作台与 Python 应用嵌入。采用一个参考任务检验接口：读取允许目录中的资料，生成审阅结论与待办草稿，经用户批准后写入指定输出目录。

这个任务应复用现有 agent_loop、工具注册表、审批和恢复，允许的工具由应用声明。读写路径受工具约束，写入需批准；不增加任意 shell 执行能力，也不把领域提示词写入内核。离线模式用于契约回归，真实模型质量仍单独记录。

文件存储存在整文件重读与重写路径，服务按请求/运行创建线程；目前缺少吞吐、内存与存储增长基线。应先收集受控持续运行数据，再判断 SQLite、队列或进程模型是否值得引入。单凭文件数量或代码行数不足以决定迁移。
