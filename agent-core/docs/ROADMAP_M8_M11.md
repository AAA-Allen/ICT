## 阶段目标

把当前通用运行框架推进到可供受控单机应用稳定接入的候选版本。应用应能通过公开接口调用模型和工具，在失败、审批和重启后解释已发生的事实，并通过可复现的验收用例验证这些承诺。

按 M8 → M9 → M10 → M11 顺序推进，以验收结果进入下一项；不预先承诺发布日期。健身业务继续在 ICT2 独立维护。

2026-11-08 调整：M10 真实模型配置缺失，先推进可独立验证的 M11 安装、兼容文档及 CI 接线。该准备不替代 M10 真实验收，发布条件仍保留真实模型、许可证和远端矩阵检查。

## 基线与选题依据

- 已有 Graph Runtime、持久化、checkpoint、生命周期、HTTP 工作台及 Harness M0–M7。
- `llm`、`agent_loop`、声明式 `tool` 已使用 Harness；自定义节点直接使用 `ctx.model`、`ctx.tools` 仍不会自动获得调用审计与额度约束。
- M7 的普通工具审批快照已使用 `state_version` 区分节点重放和后续访问；`agent_loop` 仍按节点查找旧快照，未采用同一判断。循环图是否误用已完成审批结果需要先用回归用例复现并收口。
- 恢复事实分布在运行结果、checkpoint、调用审计和审批私有快照中，需要以故障矩阵验证其一致性。
- 当前测试主要验证框架契约；尚不能据此判断真实模型在应用任务中的完成质量。
- 服务按本机单实例设计，已有可选审批 token，不具备完整用户认证或多租户隔离。

## M8：恢复契约收口

### 任务

1. **M8-01：先补循环图回归用例。** 覆盖普通 `tool` 和 `agent_loop` 在同一节点第二次访问、连续两次审批、重启后恢复、完成结果重放的行为。记录现状，避免仅凭实现推断缺陷。
2. **M8-02：统一审批调用身份。** 明确运行、节点、节点访问与审批请求的关联规则；将模型循环与普通工具的恢复判断对齐。对历史无 `state_version` 快照制定兼容规则：可以明确拒绝歧义恢复，不得静默视作新的调用。规则先写入阶段设计，再实现。
3. **M8-03：建立故障矩阵。** 在预算占用、外部调用、工具结果落盘、预算结算、checkpoint 提交处分别注入失败，使用新 Runtime 和同一持久目录恢复。覆盖模型、只读工具、需审批的副作用工具和同步子 Agent。
4. **M8-04：固化恢复结果与原因码。** 区分可恢复、需重新批准、需人工核对、不可恢复；核对 HTTP 查询、`resumable` 和 `/resume` 的行为与实际执行一致。仅在现有码无法表达事实时新增原因码。

### 验收

- 同一次需审批调用已确认完成时，节点边界重放不再次执行工具，不再次消耗该工具尝试额度。
- 图循环产生的新访问必须生成新的审批请求；旧决定不能授权新参数或新的访问。
- 工具、参数、输出路由或审批身份不匹配时停止；拒绝决定不能被普通恢复绕过。
- 调用已开始但结果不明时不自动重发；无法自动恢复的故障窗口要在矩阵中明确列出。
- 运行级预算在重启后不重置，子 Agent 重放继续遵守既有持久结果复用规则。
- 老快照的兼容读取、拒绝原因和迁移方式有测试及文档。

### 交付物

`docs/HARNESS_M8.md`、可执行故障矩阵测试、必要的内核修复、README/CHANGELOG 更新。完成后才能继续扩大受管调用的使用范围。

## M9：自定义 Python 节点受管调用

### 任务

1. **M9-01：确定最小公开接口。** 为节点上下文提供受管的模型调用和工具调用入口。方法名在设计时定稿；明确同步返回类型、审批等待结果、取消、上下文装配、usage、异常映射与流式 token 行为。
2. **M9-02：明确配置归属。** 工具暴露范围、能力授予、节点调用额度与重试策略由装配配置决定；调用方不能通过一次方法调用扩大已授予权限。节点额度和运行额度的关系沿用现有规则。
3. **M9-03：实现共用执行服务。** 复用已有模型/工具流水线，内置 `llm`、`agent_loop`、`tool` 和自定义节点从同一实现获得审计、预算和恢复行为，避免再增加一套独立循环。
4. **M9-04：提供迁移路径。** 写一个自定义节点示例，展示从原始适配器调用迁移到受管接口。现有 `ctx.model`、`ctx.tools` 和基础工具适配函数保留明确的低层调用边界；不得宣称框架能拦截任意 Python 代码中的外部操作。

### 验收

- 同一工具在内置节点和自定义节点调用时，权限拒绝、审批、预算与审计结果一致。
- 自定义节点的模型调用、工具调用、重试以及同步委派消耗同一运行额度。
- 审计失败、取消、额度耗尽和结果不明均能在副作用发生前阻止不允许的新调用。
- 需要审批的自定义调用能进入等待，并按 M8 契约重启恢复；等待不能被包装成成功。
- 公开接口的测试覆盖正常、失败、审批和恢复路径；应用不必使用私有字段组装流水线。
- 既有公开 Python API 与配置的兼容策略写清，破坏性调整才进入版本迁移清单。

### 交付物

`docs/HARNESS_M9.md`、公开调用 API、自定义节点迁移示例、内置节点共用实现及契约测试。

## M10：应用验收与模型证据

选择两个无须外部账号的通用场景：本地资料审阅、任务分流。应用提示词、工具和判断规则放在 `examples/`，领域规则不进入框架内核。

### 任务

1. **M10-01：固定输入和预期。** 每个场景定义输入资料、允许工具、预期产物、拒绝或人工介入条件。初始用例包含成功、证据不足、权限不足、调用失败、预算耗尽、审批及重启恢复。
2. **M10-02：建立离线验收入口。** 使用明确标注的确定性模型替身验证编排、审计和恢复。通过本机 HTTP 模型替身验证适配器与 Harness 的接线；不将替身输出作为真实模型效果证据。
3. **M10-03：执行真实模型检查。** 有可用服务端配置时，由独立命令运行固定输入，记录模型标识、输入版本、配置、终态、原因码、调用次数和实际返回的 usage。缺少配置时明确记为未执行，真实模型验收项保持未完成。
4. **M10-04：输出可复查报告。** 将框架契约是否通过、任务产物是否满足预期、模型行为是否稳定分别记录。缺失 usage 不估算 token 或费用，报告中不保存密钥。

### 验收

- 两个场景共用同一内核与公开调用接口，无须修改 `agent_core` 的领域规则。
- 离线用例可重复运行，并检查明确的状态、执行次数与预期产物。
- 真实模型报告允许失败或阻断，但每个结论必须能对应实际运行证据；模型错误不能被改写成框架成功。
- 模型任务质量标准在运行前固定，避免依据输出临时改变通过条件。
- 场景验收结果可由运行记录和脚本复查，无须新建通用评测平台。

### 交付物

两个通用示例、固定验收数据、运行命令、离线检查及真实模型报告模板/实际报告。真实模型配置未就绪时，报告保留明确的未验收项。

## M11：候选版本交付

### 任务

1. **M11-01：包安装验证。** 构建 wheel，在没有仓库源码路径的干净虚拟环境中安装，验证 Python API、CLI、内置工作台静态资源和示例配置。开发测试依赖要能按文档安装。
2. **M11-02：核对跨平台回归。** 按现有 CI 的 Windows/Linux、Python 3.10/3.13 矩阵检查新能力，记录实际结果；不以单机测试替代远端 CI 结果。
3. **M11-03：整理公开契约。** 更新 API、原因码、存储版本、恢复限制、单实例边界和迁移说明；给旧评估及历史开发记录增加当前入口，避免混用历史缺口与当前状态。
4. **M11-04：完成发布决策。** 核对许可证、版本号、依赖和发布清单。许可证由维护者确认；存在公开 API 破坏性调整时按 `0.x` 策略发布次版本。发布或推送仍需明确的发布指令。

### 验收

- 干净环境可按文档完成安装、启动、一次调用与失败查询。
- README、阶段文档、示例与实际 API 一致，未验收能力有明确标记。
- 无未说明的持久化格式或配置破坏；回归结果、待决事项和版本范围可审查。
- 许可证或必要模型验收未完成时保留发布阻断项，不将计划状态改为已发布。

## 后续选题的启动条件

| 选题 | 何时启动 |
| --- | --- |
| 完整 HTTP 身份认证与调用方权限 | 需要非本机访问，或确实存在多个调用方隔离需求时 |
| SQLite/事务型运行存储 | 故障矩阵、文件存储性能数据或多进程需求证明必要时 |
| 并行节点、任务队列、跨进程预算 | 出现可量化的并发工作负载，并确定恢复与预算模型后 |
| RAG、长期记忆、更多模型集成 | 两个应用场景暴露出明确能力缺口时 |

上述选题独立立项，不作为当前单机候选版本的隐含承诺。
